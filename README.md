# ShiftEarnings — персональный live‑учёт заработка по сменам

Нативное iPhone‑приложение на SwiftUI для персонального учёта фактически заработанных денег. После первичной настройки ставка, смена, календарь, перерывы и история условий хранятся локально. Обычный запуск приложения не выполняет сетевых запросов.

## Требования

- Xcode 15 или новее;
- iOS 17.0+;
- iPhone (targeted device family: iPhone);
- Swift 5 language mode;
- сторонние зависимости отсутствуют.

Откройте `ShiftEarnings.xcodeproj`, выберите target **ShiftEarnings**, задайте свой `Development Team` в **Signing & Capabilities** и при необходимости замените `com.example.ShiftEarnings` на собственный уникальный Bundle Identifier. Для симулятора команда разработки не обязательна; для установки на физический iPhone и архива требуется обычная подпись Apple Development/Distribution.

## Архитектура

Проект разделён по ответственности:

- `Models/` — чистые domain‑модели и snapshots;
- `Persistence/` — SwiftData‑сущности и `AppRepository`;
- `Services/EarningsEngine.swift` — единый источник истины для финансовых расчётов;
- `Services/WorkScheduleService.swift` — построение смен и математическое пересечение перерывов;
- `Services/NotificationPlanBuilder.swift` — чистое построение плана уведомлений;
- `Services/NotificationScheduler.swift` — синхронизация плана с `UNUserNotificationCenter`;
- `Services/TimeVerificationService.swift` — ручная HTTPS‑сверка времени;
- `ViewModels/` — подготовка агрегатов для live‑экрана;
- `Views/` — onboarding, главный экран, календарь, настройки и редакторы;
- `Utilities/` — календарные ключи, Decimal‑математика и форматирование;
- `ShiftEarningsTests/` — unit‑тесты расчётов, плана уведомлений и SwiftData persistence.

SwiftUI‑экраны не считают зарплату самостоятельно. Они получают результат из `EarningsEngine` через snapshots данных репозитория.

## Как считается заработок

День идентифицируется календарной датой в рабочем часовом поясе. Для каждого дня `EarningsEngine`:

1. выбирает последнюю `WorkConfiguration`, у которой `effectiveFrom <= день`;
2. строит абсолютный интервал смены `начало + длительность`, поэтому смена может переходить через полночь;
3. берёт только фактически прошедшую часть смены относительно системного `Date()`;
4. вычитает только пересечения с **неоплачиваемыми** перерывами;
5. оплачиваемые перекуры не вычитаются;
6. добавляет ручную переработку отдельно;
7. переводит оплачиваемое время в целые миллисекунды и считает деньги через `Decimal`.

Формула базового начисления:

`hourlyRate × paidMilliseconds / 3_600_000`

`Float` для денег не используется. На экране сумма округляется банковским округлением до двух знаков и форматируется русской локалью, например `12 781,91 ₽`.

Плавность UI не является источником истины. В обычном режиме главный экран обновляется примерно раз в секунду, в плавном — примерно 10 раз в секунду. При каждом обновлении сумма вычисляется из фактической разницы дат. После закрытия приложения никакой финансовый таймер не работает; при следующем запуске результат сразу восстанавливается из текущего системного времени.

## История ставок и условий

`WorkConfigurationEntity` — effective‑dated версия условий. Она содержит:

- ставку;
- время начала смены;
- длительность;
- рабочий UTC‑offset;
- снимок расписания перерывов.

В настройках пользователь выбирает **«Применить изменения с»**. Сохранение создаёт или обновляет версию ровно с этой даты; версии более ранних дат остаются в базе. Поэтому изменение ставки в октябре не пересчитывает сентябрь.

`Считать заработок с` хранится отдельно в `AppPreferenceEntity` и определяет нижнюю границу статистики «За всё время».

## Рабочий часовой пояс

По умолчанию onboarding предлагает **Икабья · UTC+9 · +6 к Москве**. Пользователь может выбрать фиксированный offset UTC от −12 до +14. Смена, календарный день, перерывы и статистика интерпретируются в рабочем offset, а не в текущем географическом часовом поясе iPhone.

Системное время устройства остаётся источником `Date()`. Если пользователь вручную меняет дату/время iPhone, приложение ожидаемо пересчитывается. `RootView` реагирует на foreground, смену календарного дня, системного часового пояса и `UIApplication.significantTimeChangeNotification`.

## Выходные и переработка

`DayOverrideEntity` хранит индивидуальное исключение конкретной даты:

- `isDayOff`;
- `overtimeMinutes`;
- строковое Decimal‑поле коэффициента, сейчас всегда `1` (архитектурный задел без навязывания 1.5×/2×).

Выходной обнуляет обычную смену. Переработка остаётся самостоятельным оплачиваемым временем и может существовать на выходном. На обычном дне переработка добавляется поверх базовой суммы.

## Перерывы

Начальные значения:

- 10:00–10:20 — «Перекур», оплачиваемый;
- 12:00–13:00 — «Обед», неоплачиваемый;
- 16:00–16:20 — «Перекур», оплачиваемый.

Перерывы редактируются в настройках и входят в versioned‑конфигурацию. `WorkScheduleService` не вычитает перерыв целиком «по шаблону»: используется математическое пересечение интервалов. Пересечение существует только когда его длительность строго больше нуля, поэтому касание ровно в момент начала/окончания смены не считается рабочим перерывом. Перерыв вне смены не влияет на деньги, а частично пересекающийся неоплачиваемый перерыв вычитает только общую часть.

## Локальные уведомления

Разрешение запрашивается только после включения главного переключателя уведомлений. Внутренний переключатель и системный permission — разные состояния: если iOS запретила уведомления, интерфейс показывает предупреждение и кнопку перехода в Settings.

Для каждого стабильного ключа перерыва хранится `NotificationRuleEntity`:

- стандартные интервалы до начала;
- стандартные интервалы до окончания;
- пользовательские интервалы до начала;
- пользовательские интервалы до окончания.

Доступны 30/20/15/10/5/1 минут и «в момент события», плюс custom‑интервалы 1…720 минут. Можно выбрать несколько одновременно и применить схему ко всем перерывам.

`NotificationPlanBuilder` строит только будущие события, исключает выходные и перерывы вне смены, использует детерминированные identifiers и сортирует события по времени. Для ночной смены после полуночи builder отдельно сохраняет ещё не наступившие события смены, начавшейся предыдущим календарным днём. Перерыв считается пересекающимся со сменой только при строго положительной длительности пересечения; простое касание границы не создаёт уведомлений.

`NotificationScheduler` создаёт ближайшее скользящее окно максимум из **56** pending requests — это намеренно консервативный внутренний лимит, чтобы не заполнять системную очередь сотнями запросов. Reschedule реализован по схеме **latest-request-wins**: один сериализованный worker обрабатывает только актуальную generation, stale generation прекращает добавление и точечно удаляет уже завершившийся in-flight `add`, прежде чем применяется новый план. Очередь пересоздаётся после изменения настроек/календаря, при запуске и при возвращении приложения в foreground.

Выключение главного переключателя немедленно удаляет pending notifications, но правила остаются в SwiftData. Повторное включение использует прежние интервалы. **«Сбросить настройки уведомлений»** очищает только все четыре набора интервалов; расписание перерывов, ставка, история и календарь не меняются.

## Сверка времени

Обычная работа полностью офлайн. Сеть используется только после явного нажатия **«Сверить время»**.

`TimeVerificationService` выполняет HTTPS‑запрос к Cloudflare trace и читает серверный Unix timestamp. Если этот источник недоступен, выполняется HTTPS `HEAD` к Apple и используется стандартный HTTP `Date` header. В запрос не включаются ставка, заработок, календарь, переработки или иные финансовые данные пользователя.

Экран показывает:

- время устройства;
- проверенное интернет‑время;
- разницу `устройство − проверенное время`;
- фактически использованный источник.

Результат проверки **не** подменяет `Date()` и не корректирует начисление.

## Persistence и приватность

Основные данные сохраняются в SwiftData. `UserDefaults` как база истории не используется. Приложение не содержит аналитики, рекламы, регистрации, трекеров, облачной авторизации или банковских интеграций. Полное удаление приложения удаляет локальную базу — это ожидаемое поведение текущей версии.

Если постоянное SwiftData‑хранилище не удаётся открыть, приложение не аварийно завершается: оно пытается запуститься во временном in‑memory режиме и явно показывает предупреждение о том, что изменения этой сессии не сохранятся.

## Permissions и capabilities

Для локальных уведомлений используется стандартный `UNUserNotificationCenter`; отдельный entitlement не требуется. Push Notifications capability и Background Modes не включены, потому что серверные push‑уведомления и постоянная фоновая работа не используются.

HTTPS‑сверка работает через обычный `URLSession` и ATS‑совместимые `https://` адреса. Геолокация, контакты, фото, микрофон и трекинг не запрашиваются.

`EarningsEngineTests` покрывает:

- 0 ₽ до смены;
- ровно одну ставку через час;
- оплачиваемый перекур;
- остановку на неоплачиваемом обеде и продолжение после него;
- фиксацию после конца смены;
- выходной;
- выходной + переработку;
- обычный день + переработку;
- смену ставки по effective date;
- месячный агрегат;
- границу «За всё время»;
- ночную смену через полночь;
- выбор предыдущего календарного дня как live shift-anchor после полуночи;
- нулевое пересечение при простом касании границы смены;
- рабочий UTC+9 независимо от часового пояса телефона;
- округление копеек.

`NotificationPlanBuilderTests` покрывает master on/off/re‑enable, несколько интервалов, custom‑интервал, сброс, выходной, отсутствие дублей, изменение времени перерыва, отдельные правила обеда, границу даты начала работы, ограничение скользящего окна, сохранение событий активной ночной смены после полуночи и отсутствие уведомлений для break, который только касается границы смены.

`NotificationSchedulerTests` покрывает after-midnight reschedule для активной смены предыдущего дня и concurrency regression **latest-request-wins** с намеренно подвешенным первым `add`.

`DashboardRegressionTests` проверяет, что после полуночи live snapshot и live-агрегаты продолжают использовать смену, начавшуюся предыдущим календарным днём.

`RepositoryPersistenceTests` покрывает сохранение правил между экземплярами репозитория, сохранение выбранных интервалов при выключении/повторном включении, сброс только notification rules без удаления перерывов/условий, сохранение календарного исключения и настоящий disk-backed round-trip через новый `ModelContainer` на том же временном store URL.

Всего в проекте **40 XCTest‑сценариев**. 32 теста чистого доменного ядра реально скомпилированы и выполнены в доступном Swift 6.2 toolchain: **32/32 успешно**. Дополнительно оба `NotificationSchedulerTests` скомпилированы и выполнены тем же Swift toolchain через API-совместимые локальные stubs `UserNotifications`: **2/2 успешно**. Шесть тестов, зависящих от настоящего SwiftData/UI-app module (`5` persistence + `1` dashboard), требуют Apple SDK и запускаются в Xcode через **Product → Test** (`⌘U`).

## Сборка

1. Откройте `ShiftEarnings.xcodeproj`.
2. Выберите scheme **ShiftEarnings**.
3. Для симулятора выберите любой iPhone с iOS 17+ и нажмите **Run**.
4. Для физического устройства откройте **Signing & Capabilities**, выберите свою Team и уникальный Bundle Identifier.
5. Никакие API‑ключи, сертификаты или секреты в проект добавлять не нужно.

## Как получить IPA

Для распространения нужен действующий Apple Developer signing setup.

1. В Xcode выберите **Any iOS Device (arm64)** / реальное устройство как destination.
2. Выполните **Product → Archive**.
3. В Organizer выберите архив → **Distribute App**.
4. Выберите подходящий способ: App Store Connect, Ad Hoc, Development или иной доступный вашей учётной записи.
5. Xcode подпишет экспорт в соответствии с выбранной Team и provisioning profile. Секретные сертификаты и private keys в репозиторий не помещаются.

## Важное ограничение проверки в текущем репозитории

Исходники и `project.pbxproj` рассчитаны на iOS SDK, SwiftUI, SwiftData, UIKit и UserNotifications. Для окончательной compiler/linker‑проверки нужен macOS с Xcode: доступный здесь Linux Swift toolchain не содержит iOS SDK и не может выполнить `xcodebuild`. Чистое доменное ядро при этом отдельно компилируется Swift 6.2, а его 32 исполняемых теста проходят без ошибок; оба scheduler concurrency-теста также проходят в отдельном harness с API-совместимыми stubs UserNotifications. Исходный код не содержит незавершённых реализаций или сторонних пакетов.
